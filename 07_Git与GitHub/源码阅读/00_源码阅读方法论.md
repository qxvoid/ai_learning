# 00 · 源码阅读方法论

> 能写代码是一种能力，能**读懂别人精心写过的代码**是另一种，而且是你从“会调包”走向“能做系统、能改框架”的关键一步。
>
> 你目标是 AI 路线。以后你一定会打开 PyTorch、FastAPI、scikit-learn 的源码。这一篇教你**怎么读**，而不是一上来就被几十万行 C 代码劝退。

---

## 1. 为什么要读开源源码

- **API 设计的天花板**：你写的类为什么别人觉得难用？读 requests、Flask 这种“API 极简、内部复杂”的库，看它们怎么把复杂度藏在简单的 `requests.get(url)` 后面。
- **遇到 bug 时不慌**：报错栈跳进第三方库时，你能看懂它大概在哪、为什么抛错，而不是复制报错去搜。
- **站在巨人肩膀上**：你做 AI 后端、爬虫、ML pipeline，最终都要站在这些库上面。知道它们内部怎么组织，才能正确地用、正确地扩展。
- **面试与工程能力**：能讲清“requests 的 Session 是怎么管理连接池的”，比背八股文有说服力得多。

> 但要有正确预期：读源码**不是把每行都看懂**。目标是建立“架构地图”，知道各部分在哪、怎么衔接，细节用到再钻。

---

## 2. 读什么（按这个顺序，别一上来钻核心）

拿一个仓库，按下面顺序看，每一步都比上一步深：

### 第 0 层：README + 文档（10 分钟，最重要）
先搞清楚**它是干嘛的、解决什么问题、对外暴露什么 API**。不读 README 直接看代码是新手最大的浪费。

### 第 1 层：目录结构（5 分钟）
```powershell
# clone 下来后，先扫一眼骨架
# 用 VSCode 打开文件夹，靠文件树脑补模块划分
```
看它怎么分层：入口在哪、核心逻辑在哪、扩展点（middleware/plugin）在哪、测试在哪。

### 第 2 层：公开 API（入口）
找“用户从哪一行代码开始用它”。比如 requests 的用户写 `requests.get()`，那入口就是 `requests/api.py`。从入口顺着调用链往里钻。

### 第 3 层：一个最常见功能的完整调用链
挑一个你天天用的功能（比如 requests 发一次 GET），从入口函数开始，用 IDE 的“转到定义”一层层跟下去，直到你能讲清“一次请求经过了哪几层”。**一条走通的链 > 泛泛看十个文件。**

### 第 4 层：测试用例
测试是最好的“使用说明书 + 活文档”。看 `tests/` 里别人怎么调用这个库、怎么断言，比读源码快 10 倍。

### 第 5 层：核心抽象与设计模式
等你对流转熟了，再回头看它的核心类为什么这么设计（比如 sklearn 的 `fit/predict` 统一接口、Flask 的请求上下文）。

## 3. 怎么读（具体技巧）

### 3.1 用 IDE 跳转，不要用眼睛找
VSCode 里：

- `F12`：转到定义（跳到这个函数/类在哪定义）。
- `Shift+F12`：看这个东西被谁用了（查找所有引用）。
- `Ctrl+-`：退回上一次跳转位置（像浏览器后退）。
- 鼠标悬停：看类型签名和文档字符串。

> 这是读源码的核心动作：**从一个你认识的调用点跳进去，层层深入，再层层退出来。** 不要从文件第一行开始硬读。

### 3.2 画图！（你竞赛出身，这点对你特别有效）
边读边在纸上 / 白板 / Excalidraw 上画：

- **模块依赖图**：谁 import 谁。
- **调用时序图**：一次请求依次经过哪些函数。
- **类继承图**：谁继承谁。

读源码的过程，就是把脑子里那张“看不见的图”画出来的过程。画完，你就真懂了。

### 3.3 用 git log / git blame 理解“为什么这么写”

```powershell
git log --oneline -- 某文件.py       # 这个文件经历过哪些改动
git blame 某文件.py                  # 每一行最后是谁、哪次提交改的
```

`git blame` 能看到某段代码是哪个 PR、为了解决什么问题加的——顺着提交信息往往能读懂作者的意图。

### 3.4 带着问题读，别当小说读
漫无目的地读 = 半小时后走神。每次开始前给自己一个具体问题，比如：

- “requests 的 `Session()` 是怎么复用 TCP 连接的？”
- “Flask 的 `@app.route` 装饰器到底把函数注册到哪了？”
- “sklearn 的 `fit()` 内部约定是什么，为什么所有 estimator 都长一个样？”

带着问题，你看代码时才知道哪些行重要、哪些可以跳过。

### 3.5 先略读，再精读
第一次通读一个大文件，允许自己“假装看懂”。用注释标出哪段大概是干嘛的，**先建立全局印象**。之后带着问题回来精读具体段落。试图第一遍就懂每一行，是读不完任何大项目的。

### 3.6 读不下去怎么办（正常现象）

- **C/C++ 占比高**（如 PyTorch、NumPy 核心）：先读 Python 层封装，知道对外 API 怎么组织，C++ 实现“知道在那、先跳过”。你是为了学架构，不是为了重写 CUDA kernel。
- **文档缺失**：直接去看 `examples/` 或 `tests/`，跑一个最小例子，在关键函数打断点 / 加 print，看数据流。
- **被细节淹没**：退回到上一层，问自己“我现在要解决的问题是什么？这段代码在我的问题里扮演什么角色？”无关的细节大胆跳过。
- **实在读不动**：换个更小的同类库。读不动 Flask 就先读它作者写的更小的 Werkzeug/Click，台阶要一级一级上。

## 4. 怎么做笔记（让读的东西沉淀下来）

在你的学习目录里给每个项目建一个笔记文件，结构固定：

```markdown
# 项目名（一句话：它解决什么问题）
## 我为什么读它（呼应我哪条学习线）
## 架构地图（画的图/文字描述分层）
## 入口：用户从哪进来
## 我跟踪的一条调用链（A → B → C → D，每步干了啥）
## 我学到的一个设计点（比如：它怎么把复杂藏在简单 API 后）
## 还没搞懂、下次再来看的问题
```

> 不记笔记 = 一周后全忘。笔记不必好看，能让你两周后 5 分钟回忆起来就算成功。

## 5. 一个最小可行流程（今天就能做）

1. clone 一个小项目（推荐 pallets/click，才几千行）。
2. README 读一遍，知道它是个写命令行工具的库。
3. 写一个 5 行的小脚本用它。
4. VSCode 打开，`F12` 跳进你调用的那个装饰器。
5. 画一张“我的命令从输入到执行经过了哪几步”的图。
6. 写半页笔记。

完成这六步，你就完成了人生第一次“读懂开源项目”。下一篇给你具体路线。
